# QKil

QKil is a pest control management platform for small and mid-sized UK
operators. It covers the whole job lifecycle in one place: capture a customer,
quote the work, schedule the visit, let the technician file a photographic
inspection report from their phone, raise the invoice automatically when the
job is signed off, and chase the money. A FastAPI + MongoDB backend serves a
React single-page app, with generated PDF quotes, invoices and inspection
reports branded from a single company settings document.

## Architecture

```
                            ┌──────────────────────────────┐
                            │        Browser (SPA)         │
                            │  React 18 · Vite · Tailwind  │
                            │  Zustand · React Router      │
                            └──────────────┬───────────────┘
                                           │  JSON over /api/v1
                                           │  Bearer access token (in memory)
                                           │  Refresh token (localStorage)
                                           ▼
                            ┌──────────────────────────────┐
                            │        FastAPI backend       │
                            │                              │
                            │  routers/   HTTP + validation│
                            │  services/  business logic   │
                            │  models/    Beanie documents │
                            │  core/      JWT, RBAC        │
                            └───────┬──────────────┬───────┘
                                    │              │
                    Motor (async)   │              │  reportlab
                                    ▼              ▼
                        ┌───────────────────┐  ┌──────────────────┐
                        │      MongoDB      │  │  Generated PDFs  │
                        │                   │  │                  │
                        │ users             │  │ Quote            │
                        │ customers         │  │ Tax invoice      │
                        │ quotes            │  │ Inspection report│
                        │ bookings          │  └──────────────────┘
                        │ jobs · photos     │
                        │ invoices          │
                        │ notifications(TTL)│
                        │ company_settings  │
                        │ counters          │
                        └───────────────────┘
```

Every response uses the same envelope, and every list endpoint nests pagination
inside `data`:

```json
{ "data": { "items": [], "total": 42, "page": 1, "page_size": 20 },
  "message": "42 customer(s) found",
  "success": true }
```

Errors keep the shape with `success: false`; validation failures also carry
`data.errors` with per-field detail.

## Features by phase

- **Phase 1 — Foundations** ✅
  JWT auth with refresh rotation, role-based access control (admin / office
  staff / technician), staff account management, customer database with search,
  filtering and soft delete.
- **Phase 2 — Quotes** ✅
  Line-item quotes with VAT, auto-numbered `QTE-0001`, lifecycle state machine
  (draft → sent → accepted / rejected / expired), branded PDF export.
- **Phase 3 — Bookings** ✅
  Calendar scheduling, technician assignment, recurrence, conflict-aware status
  transitions, conversion from an accepted quote.
- **Phase 4 — Jobs & inspection reports** ✅
  Mobile-first technician portal, inspection findings with severity, treatments
  applied with SDS references, photo upload, customer and technician signature
  capture, full photographic PDF report.
- **Phase 5 — Invoicing & payments** ✅
  Invoices raised automatically when a job completes, partial payments, overdue
  sweeping, dashboard revenue aggregation, tax invoice PDF.
- **Phase 6 — Global search** ✅
  One endpoint across customers, quotes, bookings, jobs and invoices, fanned out
  in parallel with batched name resolution. Header quick-search with recent
  searches plus a full results page.
- **Phase 7 — Notifications & reminders** ✅
  In-app notification bell with unread badge, reminders for tomorrow's bookings,
  imminent visits, overdue and soon-due invoices, job follow-ups and expiring
  quotes. De-duplicated, generated by a passive sweep, expired automatically by
  a 30-day TTL index.
- **Phase 8 — Company settings** ✅
  Singleton settings document driving company profile, logo, invoice and quote
  defaults, SMTP configuration (stored, not yet active) and the PDF accent
  colour.

## Quick start

### Backend

```bash
cd backend

python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

pip install -r requirements.txt

cp .env.example .env
# Set a real SECRET_KEY:
#   python -c "import secrets; print(secrets.token_urlsafe(48))"

# With MongoDB running:
python -m scripts.seed            # create anything missing
python -m scripts.seed --reset    # wipe and re-seed

uvicorn app.main:app --reload --port 8000
```

- Swagger: http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc
- Health: http://localhost:8000/health

### Frontend

```bash
cd frontend

npm install
npm run dev       # http://localhost:5173
```

Vite proxies `/api` to `http://localhost:8000`, so no extra CORS setup is
needed in development.

```bash
npm run build     # bundle to dist/
npm run preview   # serve the production build locally
```

## API documentation

The full, always-current API reference is generated from the code and served at
**http://localhost:8000/docs** (Swagger UI) and **/redoc**. The raw schema is at
`/openapi.json`.

Route groups: `/api/v1/auth`, `/users`, `/customers`, `/quotes`, `/bookings`,
`/jobs`, `/invoices`, `/search`, `/notifications`, `/settings`.

Two endpoints accept the access token as a `?token=` query parameter, because an
`<img>` or `<a download>` cannot send an `Authorization` header: the PDF
downloads and `GET /api/v1/settings/logo`.

Backend, read from `backend/.env`:

| Variable | Default | Purpose |
| --- | --- | --- |
| `MONGODB_URL` | `mongodb://localhost:27017` | MongoDB connection string |
| `DATABASE_NAME` | `qkil_db` | Database name |
| `SECRET_KEY` | *(change this)* | JWT signing key |
| `ALGORITHM` | `HS256` | JWT algorithm |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `60` | Access token lifetime |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `7` | Refresh token lifetime |
| `ENVIRONMENT` | `development` | Runtime environment |
| `CORS_ORIGINS` | `http://localhost:5173` | Comma-separated allowed origins |
| `DEFAULT_PAGE_SIZE` | `20` | Default items per page |
| `MAX_PAGE_SIZE` | `100` | Hard cap on `page_size` |

Company-level configuration — name, company number, logo, tax rate, payment terms,
document prefixes, SMTP details, PDF accent colour — is **not** environment
configuration. It lives in the `company_settings` document and is edited at
**Settings** in the UI (admin only).

## Development notes

### Roles and permissions

| Capability | Admin | Office Staff | Technician |
| --- | :---: | :---: | :---: |
| Sign in, dashboard, global search | Yes | Yes | Yes |
| View customers, bookings, jobs | Yes | Yes | Yes |
| Create / edit customers, quotes, bookings | Yes | Yes | No |
| File inspection reports on own jobs | Yes | Yes | Yes |
| View and manage invoices | Yes | Yes | No |
| Cancel an invoice, delete a draft | Yes | No | No |
| Manage users and company settings | Yes | No | No |

Roles are enforced on the server (`require_roles`) and mirrored in the UI
(`RoleGuard`, conditional buttons). **The API is the source of truth** — the UI
checks are convenience only. Search results are filtered server-side too: a
technician's search never touches the invoices collection.

### Deletion policy

Almost nothing is hard-deleted. `DELETE` on a customer or user sets
`is_active: false`, preserving history. The API refuses to deactivate the last
active admin, or the account you are signed in with. Only draft invoices,
draft quotes and pending jobs can be removed outright.

### Reminders without a scheduler

There is no cron job or task queue. `notification_service.sweep_notifications()`
is idempotent and cheap, and runs as a FastAPI background task on both
`GET /health` and `GET /api/v1/notifications` — which in practice fires far more
often than a scheduled job would. Before writing anything, the sweep checks
every candidate against the notifications already sent in the last 24 hours, so
repeated calls cannot spam anyone. A TTL index drops notifications after 30
days.

### Adding a new module

Follow the shape the existing modules use — the vertical slice is the same
every time:

1. **Model** — `backend/app/models/<thing>.py`: a Beanie `Document` with a
   `Settings.name` collection name and explicit `indexes`. Register it in
   `DOCUMENT_MODELS` in `database.py`.
2. **Schemas** — `backend/app/schemas/<thing>.py`: a `Create`, an `Update` with
   every field optional, a flat `Response`, and envelopes built on
   `ApiResponse` / `PaginatedData` from `schemas/common.py`.
3. **Service** — `backend/app/services/<thing>_service.py`: all business logic,
   raising module-level exceptions (`ThingNotFoundError`, `ThingStateError`).
   Return flattened payload dicts via a `build_<thing>_payload()` helper, and
   bulk-load relations rather than looping queries.
4. **Router** — `backend/app/routers/<thing>.py`: thin. Translate service
   exceptions into `HTTPException`, declare literal paths (`/summary`) *before*
   `/{id}`, and register it in `main.py`.
5. **Frontend API client** — `frontend/src/api/<thing>.js`: one function per
   endpoint, returning `unwrap(response)`.
6. **Hook** — `frontend/src/hooks/use<Things>.js`: owns loading, error and
   abort handling, exposing `{ data, loading, error, refetch, ...mutations }`.
7. **Pages** — `frontend/src/pages/<things>/`: list, detail and form screens,
   composed from `components/ui` primitives.
8. **Routing and navigation** — add routes in `App.jsx` (wrapped in `RoleGuard`
   where the API restricts access) and, if it belongs in the menu, an entry in `lib/navigation.js`
   (shared by the desktop sidebar and the phone tab bar; five items at most).

Conventions worth keeping: record numbers come from the atomic `Counter`
document (`Counter.next_number("job")`); status changes go through an explicit
`ALLOWED_TRANSITIONS` map rather than ad-hoc `if` statements; and anything
customer-facing in a PDF reads from `company_settings_service`, never a
hard-coded string.
